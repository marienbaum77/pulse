# Pulse

Платформа, которая превращает поток новостей в посты и дайджесты с автоматическими проверками.
Читает подключённые источники, объединяет материалы об одном событии в **сюжеты**, оценивает **вес** каждого сюжета, готовит черновик
и отправляет утверждённый текст в Telegram или webhook. По умолчанию пост ждёт редактора; автоматическую публикацию можно включить в настройках проекта.

```
Источники ─► Сбор ─► Векторы ─► Сюжеты ─► Вес ─► Черновик ─► Проверка редактором ─► Публикация
 (RSS)               (эмбеддинги)  (кластеризация)    (LLM или из источников)   (веб-интерфейс)     (Telegram, webhook)
```

## Где это запускать

**Self-hosted значит «работает на сервере, который контролируете вы», а не «на вашем компьютере».**
Никаких чужих сервисов не нужно, но и выключенный ноутбук ничего не опубликует. Pulse — обычный набор Docker-контейнеров, которому нужна машина, включённая всегда:

| Вариант | Для чего |
|---|---|
| **VPS** (любой хостинг, Linux + Docker) | **Рабочий режим.** Автопостинг по расписанию, круглосуточный сбор источников. Инструкция ниже |
| Ваш компьютер | Попробовать, настроить, поразбираться. Пока он выключен — сбора и публикаций нет |

Ориентировочные требования (зависят от того, где у вас модели):

| Где модели | Что нужно от сервера |
|---|---|
| `stub` или внешний API (облако) | 1–2 vCPU, 2 ГБ памяти — хватит |
| Эмбеддинг-модель bge-m3 локально (через Ollama) | + около 2 ГБ памяти; работает на процессоре |
| Текстовая модель 7B локально | 8–16 ГБ памяти; на процессоре пишет медленно (минуты на пост), комфортно — с GPU |

Обычный VPS без видеокарты для локальной текстовой модели неудобен. Практичный вариант: **эмбеддинги локально, текст — экстрактивным режимом или через облачный API** (см. «Модели»).

## Быстрый старт (проба на своём компьютере)

Нужен Docker.

```bash
cp .env.example .env
# заполните POSTGRES_PASSWORD, ADMIN_PASSWORD и SECRET_KEY (openssl rand -hex 32)
docker compose up -d --build
docker compose exec api python -m app.seed   # опционально: пустой стартовый проект
```

Откройте <http://localhost:8080>, войдите под `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
Создайте проект (или используйте стартовый), добавьте RSS на странице «Источники» — по одной ленте или импортом OPML.
В режиме `LLM_PROVIDER=stub` языковая модель не нужна: посты собираются из предложений источников.

> **Что проверено.** Бэкенд — 48 автотестов на настоящем PostgreSQL с pgvector; интерфейс — сквозной сценарий в браузере (API + воркер + фронтенд,
> живые обновления, утверждение → отправка). Всё это запускалось без Docker. Сами `Dockerfile`, `docker-compose*.yml`, `nginx.conf`
> и `Caddyfile` я собрать и запустить не мог — проверен только синтаксис. При первом запуске возможны мелкие правки.

## Установка на VPS (круглосуточная работа)

1. **Сервер:** Ubuntu 22.04/24.04, установлен [Docker](https://docs.docker.com/engine/install/) (с Compose 2.24+).
2. **Домен:** заведите A-запись, указывающую на IP сервера (например, `pulse.example.com`). Домен нужен для HTTPS: без него пароли и сессия идут по сети открытым текстом.
3. **Файлы:** скопируйте папку проекта на сервер (`scp -r`, `rsync` или git).
4. **Настройка:** `cp .env.example .env`, заполните `POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, `SECRET_KEY`, `PULSE_DOMAIN=pulse.example.com`, **`COOKIE_SECURE=true`**.
5. **Запуск** (с HTTPS):
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
   ```
   Caddy сам получит сертификат. Контейнеры перезапускаются сами (`restart: unless-stopped`), в том числе после перезагрузки сервера, если Docker включён в автозапуск (`systemctl enable docker`).
6. **Файрвол:** откройте только 22 (SSH), 80 и 443. База данных наружу не публикуется.
7. **Резервные копии.** Контейнер `backup` раз в сутки пишет `./backups/pulse-ДАТА.sql.gz` (хранит последние `BACKUP_KEEP_DAYS` дней, по умолчанию 14). Данные Postgres лежат в именованном томе `pgdata`: обычный `docker compose down` / обновление образов том **не** удаляет; удалит только `docker compose down -v` или ручной `docker volume rm`. Восстановление: `gunzip -c backups/pulse-ДАТА.sql.gz | docker compose exec -T db psql -U pulse pulse`.
8. **Обновление:** замените файлы проекта и снова выполните команду из п. 5. Схема базы обновляется сама при старте.

Режим публикации выбирается в «Настройках проекта» → «Публикация» и определяет, сколько самостоятельности у системы:
- **«Ручное утверждение»** — каждый пост, независимо от результатов автопроверки, ждёт вашего решения на странице «Черновики → На проверке».
- **«Полуавтоматически»** — и плановые, и ручные генерации проходят автоматические проверки (ссылки на источники, числа, длина, заголовок). Если замечаний нет — пост сразу уходит во включённые каналы; если есть — остаётся на проверке с указанием причины.
- **«Автопубликация»** — обычные замечания автопроверки не задерживают публикацию, но пустой/слишком короткий текст, неполученная короткая статья и вероятное несоответствие заданному языку остаются на проверке.

Во всех трёх режимах нужен хотя бы один включённый канал — иначе публиковать некуда, и пост остаётся на проверке с пояснением. Эти эвристические проверки не заменяют редакторскую проверку фактов.

План генерации задаётся только в разделе «Каналы и расписание»: каждый запуск выбирает указанное пользователем число сюжетов (или собирает из них один дайджест). Режим публикации не создаёт дополнительные задания и определяет только, отправлять ли готовый пост автоматически или оставить его редактору.

Очередь генерации, формирующиеся и утверждённые черновики, а также ошибки показываются отдельными вкладками на странице «Черновики» — это и есть журнал автоматизации: видно, что стоит в очереди, что пишется прямо сейчас и что ждёт решения. Если контейнер воркера перезапускается в момент генерации поста, при следующем цикле планировщика (обычно в течение минуты) такой черновик автоматически помечается ошибкой, а сюжет возвращается в «Сюжеты» для повторной генерации — он не остаётся вечно висеть в статусе «Пишется».

## Откуда берутся материалы

**Pulse сам ничего не ищет в интернете. Он читает только те RSS/Atom-ленты, которые вы подключили** на странице «Источники» (или материалы, которые вы импортировали из файла).
Поэтому включённый сервер без источников ничего нового не найдёт.
Если на странице «Обзор» есть плашка «не подключён ни один RSS-источник» — дело именно в этом.

Как подключить:
- «Источники → Добавить RSS-ленту» — одна лента: вставить адрес, «Проверить», сохранить.
- «Источники → Импортировать OPML» — сразу весь список подписок из Feedly, Inoreader и других ридеров.

Примеры адресов лент (проверьте кнопкой «Проверить»): `https://habr.com/ru/rss/news/?fl=ru`, `https://www.opennet.ru/opennews/opennews_all.rss`.
Если у ленты статус «Ошибка» — текст ошибки виден на карточке источника, подробности: `docker compose logs --tail=50 worker`.

Если новый RSS-материал содержит короткий фрагмент, Pulse поставит дозагрузку страницы статьи перед эмбеддингами и генерацией по расписанию. Он извлекает основной текст, добавляет его к RSS-фрагменту и затем продолжает обработку. Страницы ограничены 2 МБ, каждый редирект проходит SSRF-проверку; если сайт не отвечает или основной текст извлечь не удалось, исходный RSS-фрагмент останется в черновике, а автопубликацию короткого текста остановит проверка качества.

## Модели: что это и что нужно на самом деле

Путаница частая, поэтому по порядку:

- **Ollama** — это не модель, а *программа*, которая запускает модели на вашей машине (как проигрыватель для файлов). Она нужна, только если вы хотите держать модели у себя.
- **bge-m3** — модель-**эмбеддер**: превращает текст в набор чисел, по которому Pulse понимает, что две новости об одном и том же. Без неё нельзя объединять материалы в сюжеты и оценивать «близость к теме».
- **qwen2.5** — **текстовая** модель: пишет связный пост своими словами и переводит материалы, язык которых отличается от языка проекта.

Моделей две, потому что задач две и это модели разных типов: одна не заменяет другую. Для группировки по смыслу нужен эмбеддер, для синтеза — текстовая модель. Текстовая модель также используется для обязательного перевода, если язык источника не совпадает с языком проекта:

| Режим | Что нужно | Как выглядит пост |
|---|---|---|
| **А. Без моделей** (`LLM_PROVIDER=stub`) | ничего | собран из предложений источников; сюжеты находятся хуже, вес темы недоступен; при несовпадении языка черновик ждёт проверки |
| **Б. Настоящие сюжеты, экстрактивный текст** | только эмбеддер (bge-m3) | то же, что в А, но сюжеты и вес считаются по смыслу; если настроен чат-провайдер, он всё равно переведёт материал на язык проекта |
| **В. Авто** | эмбеддер + текстовая модель | модель вызывается для синтеза материалов с двумя или более разными названиями источников; один источник обрабатывается экстрактивно, если его язык совпадает с языком проекта |
| **Г. Полный (LLM всегда)** | эмбеддер + текстовая модель | связный текст со ссылками на источники |
| **Д. Облако** | ключ API провайдера | как Г, без своих моделей |

Модели после настройки Ollama можно выбирать в интерфейсе: **Система → Состояние → Модели** (список, скачивание через Ollama, смена без правки `.env` и перезапуска).

**Режим Б через Ollama** (одна модель, ~1,2 ГБ):

```bash
docker compose up -d
docker compose exec ollama ollama pull bge-m3
```
В `.env`: `LLM_PROVIDER=openai`, `LLM_BASE_URL=http://ollama:11434/v1`, `EMBED_MODEL=bge-m3`. Перезапустите: `docker compose up -d`.
В «Настройках проекта» оставьте способ «Экстрактивный» или «Авто», порог сходства подберите по разделу «Качество кластеризации» (для bge-m3 обычно 0,70–0,80).

**Режимы В/Г:** добавьте текстовую модель (`ollama pull qwen2.5:7b-instruct` или более лёгкую `qwen2.5:3b-instruct`) и в настройках проекта выберите «Авто» или «Языковая модель всегда». На Windows удобнее поставить [Ollama нативно](https://ollama.com/download) и в `.env` указать `LLM_BASE_URL=http://host.docker.internal:11434/v1` — тогда модели используют память Windows, а не лимит WSL2 у Docker Desktop.

**Эмбеддинги и текст с разных серверов.** Например, эмбеддинги — локальный Ollama, текст — облако:
`EMBED_BASE_URL=http://ollama:11434/v1` для эмбеддингов, а `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` — для облачного провайдера с OpenAI-совместимым API.

**Смена модели эмбеддингов** (например, со stub на bge-m3) безопасна: Pulse заметит смену, сам пересчитает векторы и заново соберёт сюжеты. Материалы, черновики и публикации сохраняются.

## Telegram

1. Создайте бота у [@BotFather](https://t.me/BotFather), добавьте его **администратором канала** с правом публикации сообщений.
2. `TELEGRAM_BOT_TOKEN` — в `.env`; перезапустите `api` и `worker` (`docker compose up -d`).
3. «Каналы и расписание → Добавить канал → Telegram», укажите `@имя_канала`, нажмите **«Проверить доступ»**.

«Проверить доступ» **ничего не публикует**: Pulse только спрашивает у Telegram, кто такой бот и может ли он писать в этот канал. Токен хранится только в окружении, в базу и интерфейс не попадает.

**Что уходит подписчикам.** Заголовок и текст; номера источников `[1]`, `[2]` из заголовка и текста черновика **убираются**. В конце поста выводятся названия источников-ссылок.

Если язык статьи отличается от языка проекта, модель вызывается для перевода даже в режимах «Авто» и «Экстрактивный»; если чат-провайдер не настроен, несоответствие языка отмечается проверкой черновика и не даёт его автоматически опубликовать. В режиме LLM заголовок формируется как одно короткое предложение (ориентир — до 100 символов), без маркеров источников. Если модель помещает в заголовок несколько предложений, первое остаётся заголовком, а остальное автоматически переносится в текст публикации. Названия продуктов и организаций могут оставаться в оригинальном написании.

## Пароль администратора

`ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env` применяются **только при самом первом запуске**, когда в базе ещё нет пользователей. Если стек уже запускался, изменение `.env` пароль не меняет.
Сбросить пароль:

```bash
docker compose exec api python -m app.admin reset-password                  # спросит новый пароль (для ADMIN_EMAIL)
docker compose exec api python -m app.admin reset-password --email user@example.com
docker compose exec api python -m app.admin list-users                      # кто есть в системе
```
Пароль — не короче 8 символов. Автоматически подменять пароль из `.env` при каждом старте сознательно не сделано: в рабочей системе это могло бы неожиданно сбросить пароль.

## Качество кластеризации: как проверить и настроить

**Зачем.** Главный параметр Pulse — «порог сходства»: насколько похожи должны быть два материала, чтобы считаться одним событием. Слишком высокий — одно событие развалится на несколько сюжетов,
слишком низкий — разные события склеятся. Правильное значение зависит от модели эмбеддингов и от ваших источников, поэтому его подбирают на размеченных примерах. Скрипт делает это за вас.

**Ничего устанавливать не нужно** — скрипты уже внутри контейнера `api` (`pip install` требуется только тем, кто запускает всё без Docker; см. «Для разработчиков»).

**Шаг 1. Убедиться, что всё работает.** На готовом трудном наборе (похожие события: две СУБД, два сбоя сервисов, тарифы той же компании):
```bash
docker compose exec api python scripts/eval_clustering.py --data /app/sample_data/demo_news_hard.jsonl --provider stub
```
Скрипт перебирает пороги, выбирает лучший на одной половине данных, показывает метрики на другой и перечисляет ошибки (какие события раскололись, какие склеились).
Как читать: **P** — «в сюжете нет чужого», **R** — «событие не раскололось», **F1** — их баланс; чем ближе к 1, тем лучше.
Эти данные синтетические, а `stub` — это демо-эмбеддинги, поэтому цифры показывают, что скрипт работает и что порог влияет на результат, но **не** качество на реальных новостях.

**Шаг 2. Оценка на ваших новостях** (для этого нужна настоящая модель эмбеддингов, режим Б или В):

1. Пусть Pulse поработает несколько дней, чтобы накопились материалы.
2. Выгрузите их таблицей (номер проекта — на странице «Настройки проекта»):
   ```bash
   docker compose exec -T api python scripts/export_for_labeling.py --project 1 > to_label.csv
   ```
3. Откройте `to_label.csv` в Excel / LibreOffice / Google Таблицах. Колонка **gold** — метка события; сейчас она предзаполнена текущими сюжетами Pulse (`c12`, `c13`…), строки отсортированы по сюжетам.
   Проверьте группы: материал попал не в то событие — поменяйте его gold; два сюжета на самом деле об одном — поставьте им одинаковый gold. Пустой gold — материал не участвует. Хватит 100–300 строк.
   *Предзаполненные метки идут от самого алгоритма, поэтому оценка получится оптимистичной. Для честной проверки хотя бы часть материалов разметьте с нуля (`--blank` оставляет колонку пустой).*
4. Сохраните файл (CSV, UTF-8) и запустите:
   ```bash
   docker compose exec -T api python scripts/eval_clustering.py --data - --format csv --provider openai < to_label.csv
   ```
5. Лучший порог из отчёта перенесите в «Настройки проекта → Порог сходства».

## Для разработчиков

**Если вы только пользуетесь Pulse, этот раздел можно пропустить** — он для тех, кто хочет менять код.

*Вариант 1 — через Docker (проще).* Правки в `backend/app` подхватываются сами, интерфейс обновляется при сохранении:
```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```
Интерфейс — <http://localhost:5173>, API — <http://localhost:8000> (документация — `/api/docs`). Воркер сам не перезапускается: после правок `docker compose restart worker`.

*Тесты в изолированной БД.* Тесты очищают данные перед каждым сценарием, поэтому запускайте их только через отдельный test-стек:
```powershell
.\backend\scripts\test-docker.ps1
```
На Linux/macOS: `sh backend/scripts/test-docker.sh`. Используется отдельный PostgreSQL в `tmpfs`, без опубликованного порта; временные контейнеры удаляются после завершения. При запуске `pytest` напрямую `DATABASE_URL` обязан указывать на базу с именем, заканчивающимся на `_test`.

*Вариант 2 — без Docker для приложения.* Нужны Python 3.12, Node 22 и PostgreSQL 16 с расширением pgvector:
```bash
python -m venv .venv && . .venv/bin/activate
pip install -r backend/requirements-dev.txt            # зависимости + pytest + scikit-learn (для сверки метрик в тестах)
export DATABASE_URL=postgresql://pulse:pulse@localhost:5432/pulse SECRET_KEY=dev-secret-key-dev-secret-key-1234
cd backend
createdb -h localhost -U pulse pulse_test              # один раз; тесты очищают только эту отдельную БД
DATABASE_URL=postgresql://pulse:pulse@localhost:5432/pulse_test pytest
uvicorn app.main:app --reload       # API :8000
python -m app.worker                # воркер (в другом терминале)
python -m app.seed                  # пустой стартовый проект, если ещё нет

cd ../web && npm install && npm run dev   # интерфейс :5173, запросы /api проксируются на :8000
```

Если локальная модель отвечает медленно, увеличьте `LLM_TIMEOUT` в `.env` (по умолчанию 180 секунд). При сбое тип ошибки, время ожидания и ответ OpenAI-совместимого сервера видны в черновике и журнале вызовов модели.

## Как это устроено

| Компонент | Что делает |
|---|---|
| `api` (FastAPI) | REST API, аутентификация, роли, поток событий для интерфейса (SSE) |
| `worker` | планировщик (RSS, cron), очередь задач, обработка, генерация, отправка |
| PostgreSQL + pgvector | данные и векторы, **очередь задач** (`FOR UPDATE SKIP LOCKED`), события (`LISTEN/NOTIFY`), блокировки |
| `web` (React, Vite, Tailwind) | интерфейс редактора за nginx с CSP |

Отдельных брокера сообщений и кэша нет: очередь, блокировки и уведомления сделаны средствами PostgreSQL.

- **Сюжеты.** Материал присоединяется к ближайшему сюжету, если сходство с его центром ≥ порога и сюжет обновлялся в пределах окна (по умолчанию 48 ч). Окно небольшое, поэтому поиск точный, без ANN-индекса.
- **Вес сюжета (NWS)** = Σ(вес · признак). Близость к теме — главный критерий: автоматический отбор сначала отсеивает сюжеты ниже тематического порога, а затем ранжирует оставшиеся по близости к теме. Охват источниками, авторитетность, свежесть и скорость роста — вторичные признаки. Без настоящей модели эмбеддингов («stub») близость к теме не измеряется, поэтому тематический фильтр нейтрален.
- **Контекст для LLM короткий:** из сюжета берутся репрезентативные материалы, из каждого — предложения, ближайшие к смыслу сюжета; модель ставит ссылки `[n]`, по ним строятся проверки.
- **Сюжет и черновик — разные сущности.** Сюжет — это тема, которую нашла система (группа материалов о событии, с весом NWS); он живёт, пока идут новые публикации, и в нём нет готового текста. Черновик — конкретный текст поста, написанный по одному сюжету (или дайджест по нескольким), с проверками, правками и статусом согласования. Один сюжет может дать несколько черновиков (например, «написать заново»). Сюжет можно отложить или закрыть, не создавая текста, а черновик — отклонить, вернув сюжет в работу.
- **Картинки.** В БД хранится только адрес (`items.image_url`, `drafts.image_url`), файлы не сохраняются, поэтому база не растёт. Адрес берётся из RSS (`media:content`, `enclosure`, первый `<img>`) или из `og:image` страницы статьи. Интерфейс показывает картинки через прокси API (проверка SSRF, лимит 5 МБ, только jpeg/png/webp/gif, кеш браузера 7 дней), Telegram получает файл через `sendPhoto` (для длинных постов — превью ссылки над текстом), webhook — поле `image_url`. Картинка черновика — картинка первого использованного источника; в редакторе её можно убрать или заменить картинкой другого источника.
- **Текст из нескольких источников** пишет один связный рассказ. Если модель вместо синтеза выдаёт источники по очереди или копирует их предложения, генерация повторяется один раз с уточнением, а затем откатывается на экстрактивный текст без повторов. Слабые модели (3–7B) справляются хуже: для хорошего синтеза берите 14B+ или внешний API.
- **Что выбирается для поста по расписанию.** Кандидаты — открытые сюжеты с достаточным числом материалов (и заметно выросшие опубликованные), выше порога близости к теме; они упорядочиваются по близости к теме, затем по весу. Из первых `3 × N` кандидатов модель оценивает интересность (0–10, одна короткая подсказка на сюжет, не больше 6 новых оценок за запуск, результат кешируется и пересчитывается, когда сюжет вырос в 1,5 раза), и берутся самые интересные. Оценка приблизительная, особенно у маленьких моделей: она служит сигналом «сомневаюсь». Если оценка ниже 5, автопроверка оставляет черновик редактору, в том числе в режиме «полностью автоматически». Без LLM (stub) оценка не строится, порядок остаётся по теме и весу.
- **Проверки текста эвристические:** числа, которых нет в источниках, несуществующие ссылки, доля предложений со ссылкой (порог 50%, короткие связки не считаются). Это сигнал редактору, а не гарантия отсутствия ошибок.
- **Публикация — outbox.** Одна строка на пару «черновик — канал» (`UNIQUE`), состояния `pending → sending → sent | failed | unknown`.
  Если запрос мог дойти до Telegram, но ответа нет (таймаут, 5xx, падение воркера), исход помечается `unknown` и **автоматически не повторяется** — иначе возможен дубль.
  Редактор решает на странице «Публикации»: повторить, отметить как отправленное или отменить. Webhook получает `Idempotency-Key` и подпись HMAC.
- **Расписание** защищено `UNIQUE (schedule_id, fire_time)`: слот выполняется один раз, даже если воркеров несколько.
- **Безопасность:** пароли — argon2, сессия — httpOnly-cookie, CSRF — обязательный заголовок `X-Requested-With`, роли admin/editor/viewer, ограничение попыток входа,
  защита от SSRF (внутренние адреса запрещены, редиректы проверяются), строгая CSP.
  Известное ограничение: защита от SSRF не закрывает DNS-rebinding между проверкой и запросом — на публичном сервере не давайте воркеру доступ к внутренним сервисам.

## Ограничения

- Источники: RSS/Atom и ручной импорт. Веб-скрейпинг и Telegram-каналы как источники не реализованы.
- Отправка: Telegram, webhook и «консоль» (запись в журнал воркера). Telegram-текст — HTML, лимит 3900 символов.
- Настоящие цифры качества кластеризации возможны только на ваших размеченных данных (шаг 2 выше); демо-наборы синтетические.
- Интерфейс только на русском.
